# 内置摄像头间歇性失效 —— 完整技术分析

> 2026 年 10 月 · 一台 ThinkBook 16 G7 AHP（21MU）的真实排障记录。
> 本文是所有现象、证据、排除项与最终结论的汇总，供遇到同类问题的人参考。
>
> **阅读提示**：这份文档记录的是一个**从误判到修正**的过程。第一阶段（10-11）的结论是
> 「驱动/电源管理侧问题」，第二阶段（10-19）被新证据推翻，最终指向**排线接触不良**。
> 两个阶段都保留了，因为「怎么发现判断错了」比结论本身更有价值。

---

## 一、症状

三类表现，看起来像三个不同的问题：

| 症状 | 表现 |
|---|---|
| A | 设备管理器里相机消失，相机应用报 `0xA00F4244 NoCamerasAreAttached` |
| B | 相机**在位且显示「已启动」**，但只能输出 **160×120 @9fps**，画面糊到不可用 |
| C | 两者都会在一段时间后**自行恢复**，无需重启 |

**矛盾点**：如果是硬件坏了，应该越坏越彻底；但它会自己恢复。
这说明不是「坏」，而是「某个状态」。

## 三、根因：卡在 USB 枚举的第二步

USB 枚举是分阶段握手，任何一步失败，主机看到的都是"不一样的设备"：

```
① 端口检测（VBUS 供电 + D+/D- 上拉）      ← 过了：主机知道"有东西插进来"
② 复位，读「设备描述符」前 8 字节           ← 卡在这里
③ 分配地址，读完整设备描述符
④ 读配置描述符 → 加载驱动 → 设备可用
```

Windows 记成 **`USB\VID_0000&PID_0002`，错误码 43「设备描述符请求失败」**，
只有一种含义：**设备通电了、也响应了插入，但第 ② 步拿不到描述符。**

`VID_0000` / `PID_0002` 是占位值 —— 因为没读到描述符，系统**连厂商和产品是谁都不知道**。

**关键推论**：这一步发生在**任何驱动加载之前**，所以：

- 换驱动、改权限、调电源策略，**在原理上都不可能修复它**
- 重装系统也不会改变现象（新系统照样会在同一阶段失败）
- 只可能是**电气/接触层面**：D+/D- 数据线接触不良、连接器氧化、模组控制器卡死

## 四、为什么早期的 DRIPS 现象只是"症状"

### 4.1 当时看到的事件

系统日志 `Microsoft-Windows-USB-USBHUB3` 反复记录：

```
事件 ID 196
  在系统处于空闲状态时耗尽系统电源的 USB 设备。
  USB 设备: VID: 0x174F PID: 0x1820 REV: 0x1112
  删除操作失败: QueryRemovalInitiated

事件 ID 205
  重新枚举以前在电池电量不足时删除的 DRIPS 阻止设备。
```

`0x174F:0x1820` 正是这颗相机。微软对此有专门定义：
bug check **`0x1A5 USB_DRIPS_BLOCKER_SURPRISE_REMOVAL_LIVEDUMP`** ——
*阻止顶层控制器在现代待机期间断电的 USB 设备，将被强制移除（surprise removed）。*

规则是：挂在**同一个 USB 控制器**上的所有设备必须都进入低功耗（D3），
控制器才允许进入 **DRIPS**（Deepest Runtime Idle Power State，运行时空闲最深功耗状态）。
只要有一台设备卡在 D0，整条控制器就下不去，Windows 会把那个"挡路的"强制拔掉。

### 4.2 后来的修正

单看 10-11 那天，这条因果链是完整自洽的，所以当时判断为"驱动/电源管理侧问题"。
但把时间拉长到 10-19，出现了一条它解释不了的事实：

| 日期 | 现象 |
|---|---|
| 10-05 | 运行中掉线 |
| 10-06 ～ 10-07 | **同一个物理端口**在「相机正常」与「描述符失败」之间反复横跳 |
| 10-11 ～ 10-16 | 干预后稳定 6 天，DRIPS 事件归零 |
| 10-17 ～ 10-18 | DRIPS 事件复发并密集爆发（一天内 ID196=13、ID205=15） |
| **10-19** | 冷启动后**彻底不再出现**；设备树里连幽灵记录都没有；**当日 DRIPS 事件 = 0** |

**最后一行是关键**：10-19 相机彻底消失，但当天 DRIPS 事件是 0 —— 系统根本没删过它。
如果 DRIPS 是根因，它不该在"没删设备"的日子里让设备消失。

所以更合理的解释是反过来：

> **排线接触劣化 → 相机在 Suspend/Resume 的电压瞬变中卡住、无法正确进入 D3
> → 成为 DRIPS 阻断设备 → 被系统强制移除。**

也就是说，**DRIPS 强制移除是症状，不是病。** 病在排线上。
随着磨损加重，现在连冷启动都过不了描述符握手 —— 从"间歇接触不良"走到"彻底不通"。

### 4.3 硬件侧的结构依据

《ThinkBook 16 Gen 7 Hardware Maintenance Manual》第 4 章把摄像头拆成两个独立 FRU：

- `Remove the camera cable` —— 摄像头排线
- `Remove the camera board` —— 摄像头模组板

**排线必须从屏幕侧穿过转轴走到主板**，而转轴是整机开合应力最集中的位置。
笔记本上"某个功能时好时坏、且与开合角度相关"，最典型的原因就是它。

## 五、已尝试的手段与结果

| 手段 | 结果 |
|---|---|
| 卸载/重装相机驱动 | 无效 |
| `pnputil /scan-devices` 重扫 | 无效 |
| 重启相机复合设备 | 无效 |
| 重启相机所在 USB 根集线器 | 无效 |
| 清除幽灵节点 + 占位坏节点 | 节点清掉后**立即重新出现** |
| 循环 xHCI 控制器（整条 USB 链路重枚举） | 无效 |
| 关闭快速启动（`HiberbootEnabled=0`） | 已生效，但阻止不了复发 |
| 关闭 USB 选择性暂停（电源计划 + 全局 hub 开关 + 设备级 4 项） | 曾让 DRIPS 事件归零 6 天，最终仍复发 |
| 冷启动（多次） | 无效 |
| EC 复位（关机 → 拔电源 → 长按电源键 30–60 秒） | 无效 |

> **教训**：当设备连"描述符"都答不出来时，上面这些手段一个都不该期待有效。
> 它们只适用于"设备能枚举但行为异常"的场景。

## 六、三条独立证据指向硬件

判断"是不是硬件"时，不要只看一条，要看多条是否**互相独立地**指向同一结论：

1. **枚举阶段**：失败发生在读设备描述符（早于驱动加载）→ 与软件无关
2. **节点行为**：占位坏节点清除后**立即重现** → 端口上确实有东西在通电响应
3. **时间演化**：同一端口从"时好时坏"（10-05～10-07）走到"彻底不通"（10-19）
   → 符合机械磨损的渐进过程

再加上"当日 DRIPS = 0 但仍然消失"这一点，DRIPS 解释被排除。

## 七、怎么验证到底修好没有

修完（换件后）按顺序验证，**任何一步不过都说明没修好**：

### 设备层

| # | 步骤 | 通过标准 |
|---|---|---|
| 1 | 设备管理器 → 查看 → **显示隐藏的设备** → 照相机 | `Integrated Camera` 与 `Integrated IR Camera` 均正常，无灰显/感叹号 |
| 2 | `CamFix.exe --status` | `OK=1\|cam=1\|started=1\|fmt=21\|1080p=1` |
| 3 | 通用串行总线控制器列表 | 不再有「未知 USB 设备（设备描述符请求失败）」 |

### 功能层

| # | 步骤 | 通过标准 |
|---|---|---|
| 4 | 打开「相机」应用 | 有实时画面，不是 `0xA00F4244` |
| 5 | 相机应用 → 设置 → 视频质量 | 能选到 **1920×1080**（降级时只有 160×120） |
| 6 | 设置 → 账户 → 登录选项 → 面部识别 | IR 摄像头可用（验证 `MI_02` 接口） |

### 稳定性层（最容易漏，也最关键）

| # | 步骤 | 通过标准 |
|---|---|---|
| 7 | **折角测试**：屏幕从合拢到全开逐档停留 3 秒，每档「扫描检测硬件改动」 | **全程不掉线**。某角度消失 = 排线仍有问题 |
| 8 | 合盖 2 分钟 → 唤醒 | 相机仍在，`--status` 仍为 `OK=1` |
| 9 | 连续 7 天每天 `--status` | `drips196=0` 且 `drips205=0` |

> 第 7 步是分水岭：前六步过了也可能只是"暂时通"，**修完必须做折角测试**。

## 八、给后来者的排查手法

这些是本次真正用上的，都跟"看日志猜"无关，全是**直读系统状态**：

| 目的 | 手法 |
|---|---|
| 看设备真实状态（不解析本地化文本） | `SetupDiGetClassDevsW` + `CM_Get_DevNode_Status`，判 `DN_STARTED` |
| 找"幽灵设备"的父节点 | `Get-PnpDeviceProperty -KeyName DEVPKEY_Device_Parent` |
| 精确掉线时刻 | `DEVPKEY_Device_LastArrivalDate` / `LastRemovalDate` |
| 定位"描述符失败"占位节点 | 枚举 `USB\VID_0000&PID_0002*` |
| 判断是否被 DRIPS 强杀 | `Get-WinEvent -FilterHashtable @{LogName='System'; ProviderName='Microsoft-Windows-USB-USBHUB3'}` |
| 枚举**幽灵**设备（present 枚举拿不到） | 直接读 `HKLM\SYSTEM\CurrentControlSet\Enum\USB\<hwid>\<inst>` |
| 判断是否 xHCI 控制器 | 兼容 ID 含 `PCI\CC_0C0330`（**注意：在兼容 ID 里，硬件 ID 里没有**） |
| 判断相机能否真正被应用调用 | 查 `DeviceClasses\{e5323777-f976-4f5b-9b55-b94699c46e44}`（KSCATEGORY_VIDEO_CAMERA）—— ⚠️ **设备离场后该键会残留，不能单独作判据** |

## 九、结论

**不是驱动、不是权限、不是系统配置、也不是 DRIPS。**

是一颗**穿过转轴的排线接触不良**，从"时好时坏"一路劣化到"彻底不通"。
中途撞上的 DRIPS 强制移除，是被它牵连出来的次生现象，误导了我们将近一周。

硬件问题，软件修不了。**换件，或者在保修期内报修。**
